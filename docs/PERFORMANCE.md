# 性能实测、指标与调参

本项目没有“零影响”或固定支持 1000 端点的生产容量承诺。报告保存原始实际数字；短窗口、单种 FE 负载和本机后端不能外推到大型工厂、多 JVM 热点物品组件或高延迟网络。

当前核心为 `68f32db`；最终三模式、三路径各三重复的27个窗口已完成，见文末“最终三服同条件比较”和 [完整结果](../reports/optimization-comparison-68f32db.md)。早期4cfff0a、753与925的独立实验保留版本归属，不能把它们的最佳数值拼接为当前成绩。

## 本轮比较口径（2026-10-06）

本轮基线固定为 `87bf217fcaffcceb2629c36bb54d5158b9f461e8`，运行中的类与启动参数已冻结。九次真实三 JVM 基线在 `reports/optimization-baseline-87bf217-20261006T090251Z-7859e9.json`，100/500/1000 加载规模在 `reports/performance-opt-baseline-87bf217.json`。三条路径每轮 40 笔隔离低流量探测、30 秒预热、120 秒持续观察、三次重复；固定 240 个输入事件。不同 JVM 的 nanoTime 不相减，使用同一个 Python 观察器记录真实能力接受/提取的时间区间。

基线三轮 p95 上界中位数为同服 2866.16 ms、纯跨服 2866.96 ms、混合 2912.35 ms；每 240 输入事件实际 DB 事务中位数为 3714/3657/3614。基线混合两接收者都被服务，没有广播复制。基线混合第一轮保留一次成功恢复的死锁重试，不能只挑无重试样本。原始 JSON、RCON 误差范围、旁路监控覆盖及比较命令见 [本轮基准方法](OPTIMIZATION_BENCHMARK.md)。

实现前冻结目标：同服 p95 至少降 40%、同一业务量 DB 事务至少降 30%、空闲 DB 事务至少降 30%、纯跨服 p95 回归不超过 20%，且混合接收者不能饥饿。达成与否必须按完整前后报告计算，不改变统计单位、输入事件数或目标阈值。下面所有 `performance-final/pre-stock/before/after` 表格是上一轮历史数据，不是本轮比较。

### 保留的失败规模测试与修复

`reports/performance-opt-fast-e4057a5-as-run.json` 是未修复版本的真实 120 秒窗口。500/1000 ACTIVE 各出现50/496个后台错误，1000末次仅984活跃；旁路实际窗口中活跃数912–992，不能报告为成功运行1000端点。旧脚本的 `passed=true` 仅反映脚本跑完，独立验收 `optimization-scale-e4057a5-acceptance-audit.json` 为 false，原文件和首次失败监控均保留。

`optimization-scale-e4057a5-innodb-status.txt` 记录两个频道任务对同一服务器历史配额行先取共享锁再升级写锁的真实死锁。旧代码在清理已失效的savepoint时，用MySQL1305覆盖1213，导致已有死锁重试无法识别。`75392af` 改为保留主异常和附加清理异常，历史行首次触碰即取得写锁；不删除余额/权限锁、不忽略历史限额。清洁且关闭SEND的持久TX pending不再触发无业务SQL；资源和业务ID仍保存在WAL，恢复与重新开启SEND仍会调度。真实MySQL双连接死锁和本地持久OFF测试通过。

失败版本1000 OFF仍有残留任务，不能视为排空后的空闲成本。部分极小浮点耗时被旧解析器的科学计数法截断，这些小分位数不作性能比较；整数事务、资产量和实际错误不受该解析缺陷影响。修正版脚本识别指数，保持超过2^53的整数精度，并将错误、拒绝、端点不足或新增隔离判为失败。失败规模的离线数据见 `optimization-scale-comparison-e4057a5.json/.csv`。

基线 1000 OFF 与 ACTIVE 的只读旁路仅实际覆盖各约 118 秒子区间，分别为 862/75994 个事务，即 7.305072/644.022995 tx/s。ACTIVE 队列 84–96、该子区间死锁重试 92 次；两段任务失败/拒绝/隔离为零。不能使用累计结束计数冒充整个 120 秒窗口的事务增量，也不能把测试后 OFF 回收尾部混入空闲基线。100/500/1000 的现有规模脚本只有五秒预热、单次 120 秒观察；不满足长期容量或三次重复要求。

新指标仍须按其定义使用：`local_credit_publications` 是本目的端全部新凭证应用数量，不证明源也在同服；`local_input/output_units` 混合资源单位且输出包括可能被真实能力 remainder 撤回的本地领取，不能替代净外部吞吐。`batch_devices/records/payload_bytes` 反映合并工作量，`db_transactions` 才是实际成功 SQL 事务。WAL 写入/字节/持久化屏障在新版本有真实计数，原基线没有该计数，不能补填或推算 WAL 降幅。整服原生 recorded tick 指标的范围不包括所有外层任务；完整 wall MSPT 与实测 TPS 若没有独立测量，仍标为未测。

负载生成器每 tick 最多十六次真实 FE 能力调用，发送端输入 1000 FE、接收端最多提取 32000 FE；输入上限由生成器调用频率和轮转决定，并不是后端处理极限。吞吐用实际接收端提取量/实际秒数计算。生成器耗时单独记录 `fixture_ms_per_tick`，不计入模组 Runtime 的工作耗时。即使同服端点，也走相同 SQL 权限/所有权路径。

加载由测试 fixture 的 vanilla 票据保持，OFF/active 时区块和设备相同；它们不是本模组配额实现。没有其他工厂机器。因此本实验测量 A：本模组额外工作；B：强制加载后其他机器持续运行的额外成本**未测**。不能将 B 隐藏，也不能用本实验解释实际大型工厂的总 MSPT。

## 指标的准确含义

- `tick_ms_*`：Runtime 主线程工作滚动最多 2048 样本；不包括所有 Minecraft/其他模组工作，不等于整服 MSPT。
- `db_transaction_ms_*`：Sql.transaction 实际耗时，包含连接/重试及事务中的语句；`db_deadlock_retries` 记录重试。
- `sql_ms_*`：历史名称，实际是后台任务/批次总耗时，可能含 WAL；不能解释为纯 SQL 延迟。
- `delivery_ms_*`：接收批次开始到本地额度应用的延迟，**不是**源外部机器抽取到目的机器保存的完整端到端延迟。本轮独立脚本测真实能力接受到实际提取的 E2E 区间；仍不等于目的世界持久化保存。
- `worker_queue`、`queue_rejected`、`errors`、`quarantined`、`actual_tickets`、`transactions`：当前队列/累计计数；测试窗口用差值，启动阶段错误不能从报告中抹去。

票据恢复/安装会触发 Minecraft 区块加载，单次可超出 2 ms 软预算；初次恢复不是稳态传输数据。默认每 tick 只处理两个票据变更；数据库/Redis 故障下撤销自己的实际票据优先保证失效边界。改变该预算会影响恢复延迟，不能承诺票据本身零主线程开销。

## 默认预算与调参

配置示例包含每 tick 16 端点检查、64 完成项、16 个重序列化栈、2000 µs 软预算；200 ms 批次、每批最多八个发送记录、128 后台队列、4 SQL 连接。空闲轮询下降到两秒，达到容量/队列阈值返回零或剩余形成背压。物品九个 TX 槽、流体四个 TX 槽、化学品四个 TX 槽，接收凭证上限 64；FE 默认 2000000、EU 默认 16777216。

热点频道的 SQL 余额锁、不同组件种类的序列化/WAL 和记录数量通常比单个 FE 数值更重要。先看队列、实际事务、数据库分位数和 JFR，再改预算；不要通过无限队列掩盖不足。所有这些启动配置需要重启，群组配额/频道限制以权威政策为准。

每服历史默认 500000 条准入，终态保留三十天。持续高 TPS 会较快达到该上限并产生背压；本次几分钟测量没有验证三十天持续容量或自动完整归档。未解决隔离、活资产及 tombstone 不能清理以强行恢复吞吐。生产需结合磁盘、备份和保留策略决定容量，并演练暂停及归档。

大型不同组件、热力延迟振荡、多子服 1000 端点热点频道、网络延迟/丢包、长期数据增长与实际其他工厂机器负载均尚未压测。
