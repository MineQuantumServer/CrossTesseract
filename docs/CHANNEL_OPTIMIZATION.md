# 频道合批与统一所有权下的本地低延迟

本轮从干净的 `main / 87bf217fcaffcceb2629c36bb54d5158b9f461e8` 继续开发，工作分支为 `perf/channel-coordinator`。没有改动已发布的 V001–V004 迁移；协议 1、资源格式 1、WAL 格式 2（仍可读 1）不变。最终代码、产物摘要和性能数值以本报告末尾的证据清单为准。

## 实际路径

基线源码逐项核验（`87bf217`，不是仅依据任务描述）：

| 切入点 | 原版实际调用 | 本轮处理 |
| --- | --- | --- |
| A 本地交换耦合 | `tick` 先跳过 inFlight/nextPoll，再 pumpNeighbors | 独立预算内本地轮转；增量回调保护期间的新输入和消费 |
| B 逐设备任务 | `transfer(TesseractBlockEntity)` 每设备提交 | Runtime 的频道队列去重、single-flight、执行中唤醒保留 |
| C 表面批次多事务 | 一个 worker 依次调用 deposit/checkpoint/allocations/demand/allocate/markLocal，各自 transaction | 第一阶段显式共享Connection；WAL后第二阶段真实合批，保留逐业务幂等ID |
| D N+1 | allocations 逐行调用 allocation，再 SELECT ct_resources | 有界批量JOIN及事务内规范载荷复用 |
| E 通知未定向调度 | drain 登记每条inbox/ACK，只返回数量 | 批量权威校验、定向hint及本地信号；ACK仍不是资产交付 |
| F 维护相互拖延 | 同一control maintain串接心跳、权限、通知和清理 | 独立有界维护/通知入口，心跳保留连接余量 |
| G 完成容量 | offer失败会暂停并计拒绝，但无法应用该终态回调 | 提交前预留有界完成位置，不称旧版无诊断，也不改成无界队列 |
| H 不可服务候选 | LIMIT首位后才检查凭证/余额profile，可挡住后续候选 | 全局有效候选按端点轮转并跳过不可服务者；没有本地优先 |

这些机制不把既有共享线程池、200ms批次、能力缓存或背压重新列为新功能。后台排队与不同业务阶段仍可能产生等待，真实改善和回归分别列性能报告。

`A1 → A2` 依次经过本地 TX、源 WAL 持久化、第一 SQL 事务、目的 WAL 持久化、第二 SQL 事务、目的 RX 和实际本地能力输出。第一SQL阶段包含有界频道批次中的检查点、独立业务 ID 的 deposits、必要的需求续期、已有凭证 JOIN 读取和公平独占划拨；第二SQL阶段在最新 WAL 落盘后重新检查会话、端点版本、原绑定和 RECEIVE 权限，推进 LOCAL 与检查点。磁盘 fsync、Redis 和主线程能力调用均不在 SQL 持锁区间。两个阶段不表示每任务固定两次事务：无新提交/凭证可省略发布阶段，最新快照超过组上限时发布阶段可拆为多个事务。

`A1 → B1` 使用同样的 SQL 所有权阶段。区别是 A2 可以收到进程内频道信号，和 A1 的就绪工作共用本子服频道批次；B1 通过验证后的定向 Redis 提示或有界权威轮询发现 SQL 状态，再执行自己的接收批次。两条路径都不是无数据库路径，也不允许先交给 A2 再补账。

新本地调度不再等待普通后台轮询周期才运行相邻交换；已发布 RX 进入有界就绪集合，在服务器主线程预算内尽快输出。新输入与旧 RX 消费可以发生在普通后台任务执行期间。回调仅删除明确已提交的原 TX ID、确认零额度 tombstone、追加尚未应用的凭证；不会用旧完整快照覆盖当前缓冲，不会恢复已消费 remaining。第二阶段 WAL 捕获此时的最新状态，SQL LOCAL 确认之后才发布新凭证。

## 合批与公平

`ChannelCoordinator` 由服务器 Runtime 管理，有界 dirty 集合、FIFO 频道轮转、逐频道 single-flight 与执行中唤醒记录。它复用共享 worker 和数据库连接池；不为每个频道或方块创建线程。默认每批最多 8 设备、256 记录、8 MiB 载荷，两阶段都校验实际记录和字节数。临时失败保留原业务 ID 和 SQL/WAL 所有权。进入 savepoint 后的端点业务错误只回滚该端点；批次 channel/world/generation 元数据预检在 savepoint 前，错误会拒绝整阶段，不声称所有非法输入都可逐端点隔离。

第一 SQL 阶段复用一个 Connection，不能在里面调用重新开启事务的公共包装。规范载荷通过 JOIN 与批次内缓存复用，仍核验完整身份与字节。outstanding allocation、inbox 通知和控制状态也做真实批读/批事务；后台 Runnable 数不作为 SQL 事务数。

`channelBatch` 先处理本批有效设备的检查点、deposits和需求，再读取outstanding并执行公平划拨；不是按设备轮流完成整套发送/接收事务。因此，同批本地接收端可以使用本批刚入账的资源，而不会因设备ID的加锁顺序恰好先遇到接收端就漏掉这次余额。它仍需成为全群组当前可服务候选并完成目的WAL/LOCAL阶段。

`A1 → A2 + B1` 的候选是全群组有效端点，按 endpoint `last_grant` 和稳定 ID 轮转。考虑当前空间、凭证上限、资源 quantum/profile、模组协议能力、权限、会话/world/epoch/generation。没有同服优先，也没有把按设备公平改成按服务器公平。不能领取的首位候选不会持续阻塞合法后续候选。领取从共享余额扣除、增加一个接收端的独占凭证；A2 的即时唤醒只改变发现与执行速度，不能让它再次消费 B1 已划拨的资产。

分配仍由请求接收端的事务领取：若全局首位是有效 B1，A2 的事务返回未分配，等待 B1 自己被通知或轮询调度；不是 A 服替任意远端发布额度。需求租约有界过期，不把过期当成已划拨资源退款。有限测试窗口验证了所有有效接收端实际得到服务，不能据此承诺任意网络分区下无限时间无饥饿。

## 调度、完成和生命周期

关键心跳/票据与权限维护、通知/历史清理有独立的有界工作入口。Redis Stream 提示经过 SQL inbox/outbox 身份校验后变成定向频道/端点信号，可合并、可丢失；权威轮询仍保留。Redis 故障的原有暂停和票据撤销策略不变，没有默认新增 SQL-only 运行模式。

`CompletionMailbox` 在提交前预留容量。SQL/WAL 已完成后，终态回调拥有预留位置，不使用可能无声失败的 `offer`；主线程不会等待队列。任务返回时核验原 BE 对象、实例 ID、捕获的频道与在途记录；旧对象不能把结果交给同坐标的新实例。卸载保留 closing 对象，等待在途工作终态后保存最新状态；拆除/隔离意图升级会重做关闭，不能被旧回调清掉。

注册恢复先在 worker 持久化恢复产生的新 revision，再交给主线程。未恢复的默认缓冲没有可提交资产；注册 SQL 确认失败并卸载时保留最新已持久化 WAL（恢复可能已提升revision），关闭不得写空检查点。主线程完成缓冲与热状态恢复之后才设置 registered。无法确认的身份/回档冲突停在明确的恢复状态，不按每秒重复登记。

性能核心之后的 `e4057a5` 追加关闭生命周期修复：未恢复设备的封存失败保留有界 Closing 重试，不提交默认空缓冲；复制相同设备 ID 的另一个 BE 对象不能移除原对象的票据或调度。只有 fresh fenced SQL 明确缺行、已知 checkpoint 为零且两个 WAL 文件明确不存在，才确认无资产结束关闭。拆除意图仍只在内存，SQL seal 前硬崩溃无法自动恢复该原因；容量拒绝也不表示已封存，保持 unclean 并需要管理员审查。

`75392af` 追加实际压力测试暴露的 MySQL 修复：事务/savepoint清理保留原始死锁异常，历史容量行先取得写锁再检查递增，避免共享锁升级死锁。已关闭SEND且清洁的持久TX pending不反复提交空SQL，但不删除资产；恢复检查点和重新启用仍会调度。真实双连接死锁回归与持久OFF测试通过，失败压测原始数据保留。

## 回退与保证范围

所有新开关只在启动读取。停止外部输入并正常停止子服，确认 clean_stop 后，以同一新版 JAR 将 `transfer.channelBatches=false`、`transfer.localFastPath=false` 重启。此模式复用相同业务 ID、WAL/SQL 所有权和恢复门；无需迁移回退、清库或重放。它不是切回旧二进制，未干净停止仍需按 RECOVERY.md 审查。

群组部署采用协调停机升级，各服核验目标产物摘要。协议/资源/WAL 格式的兼容不代表本轮已经验证新旧二进制混跑；配置 A/B/C 比较的 B、C 都使用同一新版核心。

MySQL 的原子入账与独占分配、WAL 的文件/目录持久化、区块保存、第三方容器保存仍是不同事务域。新内存输入首次 WAL 前可有掉电窗口；源或目的外部容器未保存后的回档不能自动证明资源守恒。异常能力可能已有副作用时进入隔离，不把异常当零交付再重试。故障超时、Redis ACK 和租约到期都不触发自动退款。

没有新增资产租给整服的实验协议，没有关闭 fsync 或引入未经验证的 group commit。各缓冲、批次、队列与缓存有界，但没有实现所有加载端点载荷的统一堆字节准入；1000 种最大组件载荷、真实工厂、长时间历史增长、网络延迟、整服完整 wall MSPT/TPS 和对象分配率仍需另测。

## 证据状态

最终原始 A、仅合批 B、合批加本地路径 C 的九轮各自真实三 JVM 测量已完成，共27个完整样本。A 使用冻结 `87bf217` 类文件，B/C 使用冻结 `68f32db` 类文件；每轮30秒预热、120秒稳态及40次低流量探测，原始记录与父流程互相以摘要绑定。实际结果、全部重复与未达目标见 [最终完整比较](../reports/optimization-comparison-68f32db.md)、[基准方法](OPTIMIZATION_BENCHMARK.md) 与 [性能文档](PERFORMANCE.md)。

同服 p95 上界中位数从2942.99降至405.90ms，下降86.21%；B 的实际事务三路径分别下降43.23%/44.81%/44.76%。C同服和混合事务下降29.51%/9.48%，纯跨服增加6.43%，均未达30%事务目标。C的纯跨服与混合SQL语句分别增加26.94%/31.06%；相对B，三路径WAL写入增加92.77%/148.06%/118.21%。严格比较实际返回非零，功能通过不表示所有性能目标通过。混合本地与远端接收者均有实际输出，没有同服优先策略；短窗口不能外推无限时间无饥饿。吞吐受到固定测试输入约束，不能作为峰值容量。

历史 `4cfff0a` 的27窗计时和 `75392af` 的规模回归仍独立保留，不与最终数据拼接。最终 `68f32db` ACTIVE p95 相对原版仍有38.42%/36.56%/102.46%的主线程回归。真实事务减少不等于全部性能目标达成；完整观察范围和回归见 PERFORMANCE.md 的新版规模章节。

注明版本的恢复、故障、可选兼容及拓扑报告见 [测试文档](TESTING.md)；55d87e9等历史五halt/后端故障不替代68f32db独立复测。后续比较应保留全部重复、错误、回归与观察器覆盖；baseline 没有 WAL 调用计数，不补填旧 WAL 性能数据。

## 9258a6a 的测量驱动热点修复

在原版与75392af的匹配JFR中，实际采样栈显示频道唤醒反复重建兼容资源集合，并通过接收额度列表查询空间。9258a6a仅缓存能力注册期间逐模块发布的不可变资源标识集合，将唤醒改成相同权限短路循环，并直接有界统计接收空间。已有频道端点索引继续复用；没有引入新索引、永久库存缓存、合并凭证或更改热力协议。正额度仍各占kind凭证位，零额度仍占全局64位，只有SQL确认的checkpoint才可释放；满额先返回0，再以Math.addExact求和，保留原溢出语义。

这份源码已完成67项单位/性质/真实后端测试、13项基础原生GameTest、八组合132项原生执行及冷包验证。两个新增空间边界测试覆盖部分消耗、重复credit、零额恢复记录、全局容量和无副作用探测。9258a6a的100/500/1000规模复测实际完成，但仍有主线程回归，单独保留全部结果；75392af的数值、失败记录和箱子证据不改写成新版本结果。

## 68f32db 的未消费唤醒信号短路

9258a6a的JFR仍显示 `wakeChannel` 占Runtime采样栈的大部分。68f32db在主线程查询协调器已有ready集合：同一设备已经有未消费信号时，跳过重复空间/权限探测；poll取走信号后为false，首次在途唤醒仍可记录，finish保留它安排下一批。租约本身不算未消费信号，没有跳过所有inFlight设备，也没有新增库存或授权缓存。重绑定、移除和旧完成的实例校验保留；真正capture及SQL/LOCAL发布仍重新授权。该短路仅用于频道唤醒。

这份修订的68项单位/性质/真实后端、13项基础原生、八组合132项及冷包验证全部通过，证据见TESTING.md。最终规模六窗、真实箱子六次探测和压力六窗也已实际完成；三模式重复计时独立记录，不能把历史收益改标为新修订。JAR及源码摘要见 `reports/optimization-artifact-ready-final.json`。

当前规模 ACTIVE p95 为0.508934/0.638057/1.166462ms，相对原版仍增加38.42%/36.56%/102.46%，但相对75392af下降29.09%/59.87%/56.30%。这是Runtime滚动快照，不是整窗或整服MSPT。1000端点共同约118秒观察窗的空闲事务率下降58.82%，活跃下降87.09%；原版缺完整业务窗首计数，不能补造完整120秒降幅。见 [规模对比](../reports/optimization-scale-comparison-68f32db.md) 和 [JFR摘要](../reports/optimization-jfr-68f32db.md)。
